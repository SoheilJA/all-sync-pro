Core Web Vitals Are a Revenue Line, Not a Checkbox

Every millisecond you shave off your largest paint is a line item in somebody’s funnel. Here is what LCP, CLS, and INP actually cost when they slip — and the order to fix them in when the goal is revenue, not a green badge.

Nina Petrova

Head of Engineering

On this page

  • LCP: the 2.5-second ceiling
  • CLS: trust you can measure
  • INP: the metric that replaced FID

  • The dashboard that matters

Somewhere in your backlog there is a ticket that reads “Core Web Vitals” — filed under SEO, wedged between meta descriptions and a sitemap fix. That filing is wrong — and it is exactly why the ticket keeps slipping. Core Web Vitals is not a search-engine compliance chore. It is a revenue line: three numbers describing how much of your visitors’ patience the page burns before it starts selling. Treat it like a revenue line and the prioritization writes itself.

The business case for speed

When pages get faster, conversion gets better. That is the one-line summary of a decade of performance research, and it is remarkably stable: one widely cited Deloitte study measured retail conversion lifts of roughly 8% from 100-millisecond speedups; other studies land higher, some lower. The exact figures vary by industry and baseline. The direction never does. Milliseconds are not perceptible individually, but they compound — and users experience the sum as “this site feels broken” long before they could articulate why.

The search argument is real but smaller than people think, and Google has been refreshingly consistent about it:

Page experience signals set a floor for how a page performs, but relevance still outranks speed. Among pages of similar quality, Core Web Vitals act as the tie-breaker that decides who earns the click. — Paraphrased from Google Search Central guidance on page experience

A tie-breaker sounds small until you count the queries where you and three competitors are equally relevant. And slowness taxes every marketing dollar: paid traffic that bounces at four seconds is traffic you paid full price for and received a quarter of. A fast site raises the yield on all acquisition channels at once.

LCP: the 2.5-second ceiling

Largest Contentful Paint measures when the biggest above-the-fold element — usually your hero image or headline block — finishes rendering. Google’s thresholds: good is ≤ 2.5 seconds, poor is beyond 4. In our audits, the culprits are almost always the same four, in this order of frequency:

  1. Unoptimized hero media. A 2MB PNG pushed to every device, with no preload hint, so the browser discovers it late in the parse.
  2. Render-blocking chains. CSS that imports more CSS, which requests a font, which waits for JavaScript before anything paints.
  3. Slow time-to-first-byte. $3-a-month shared hosting and an uncached CMS making the server think for 900ms before sending a single byte.
  4. Client-side rendering doing the server’s job. An empty shell that hydrates content the server could have delivered in the initial HTML.

The fixes, ranked by impact-per-hour: preload the hero and mark it fetchpriority="high"; ship AVIF or WebP at correct sizes (a 2MB hero routinely compresses to 120–180KB with no visible loss); inline critical CSS and defer the rest; self-host a subsetted variable font; and put the origin behind a CDN with full-page caching. Do those five things and most sites clear 2.5 seconds without touching framework architecture.

CLS: trust you can measure

Cumulative Layout Shift is the metric non-engineers grasp fastest: the button moves while the user is pressing it. Every shift is a mis-tap, a lost sentence, a silent verdict that the site is janky — trust erosion, quantified. Good is ≤ 0.1, and the usual suspects are predictable:

  • Media without dimensions. An <img> with no width and height gives the browser zero information, so it guesses a height of 0 and reflows when bytes arrive.
  • Font swaps without matching metrics. The fallback renders narrow; the webfont renders wide; every line reflows.
  • Late slots. Cookie banners, ads, and third-party embeds injecting themselves after first paint.

Nearly all of it collapses into one CSS pattern — reserve the space before the bytes arrive:

/* The five-line CLS fix — space is reserved before bytes arrive */
img[width][height] {
  aspect-ratio: attr(width) / attr(height); /* the browser does the math */
}

.banner-slot { aspect-ratio: 970 / 250; }   /* ad real estate, fixed  */
.video-embed { aspect-ratio: 16 / 9; }      /* embeds: no late pop-in */

@font-face {
  font-family: "Grotesk";
  src: url("/fonts/grotesk.woff2") format("woff2");
  font-display: swap;      /* readable now, upgrade soon */
  size-adjust: 96%;        /* fallback metrics ≈ real metrics */
}

/* pair with explicit width + height on every <img> and <iframe> */
.media-frame > img { height: auto; }

The size-adjust line is the one teams skip: font-display: swap alone guarantees visible text but not stable text. Tune the fallback to occupy the same width and the swap becomes invisible.

INP: the metric that replaced FID

In March 2024, Interaction to Next Paint formally replaced First Input Delay in the vitals set, and the upgrade matters. FID measured only the first tap and only the input delay portion; INP samples every interaction across the page’s lifetime and reports close to the worst case. Good is ≤ 200ms. A page can pass FID while feeling dead on its fifth click — INP exists because users noticed before the metric did.

The cause is almost always a congested main thread. Three patterns dominate:

  • Third-party sprawl. Chat widgets, A/B tools, tag managers loading tag managers — each defending itself as “just 40KB” while collectively owning the thread.
  • Long tasks. Anything over 50ms blocks input; a 300ms task during a tap is a 300ms-dead page.
  • Hydration waterfalls. Frameworks re-executing the whole tree on the client, so the page looks ready and behaves frozen.

The fixes: audit long tasks in the Performance panel and attribute every one to a script; defer or lazy-init third parties behind a facade until first interaction (chat widgets survive this fine); break long tasks with scheduler.yield() instead of one synchronous block; and if hydration is the disease, move first-priority content into server-rendered HTML — not a bigger client bundle to fix a client bundle problem.

Fix in the right order

Teams waste entire quarters fixing INP on sites whose TTFB is 900ms — retiling a sinking ship. Performance work has a dependency chain: server, then paint, then stability, then responsiveness. Work it top to bottom:

Fix-in-order checklist: metric, symptom, first fix, and how to verify
MetricSymptomFirst fixVerify with
TTFBEverything is slow; lab scores oddly fineCDN + full-page cache; leave budget hostingServer-Timing header, Search Console
LCPHero paints late on mobileAVIF/WebP hero + preload + fetchpriorityLighthouse lab run, then CrUX field p75
CLSButtons jump while readingaspect-ratio + width/height on mediaDevTools Layout Shift regions
INPTaps feel dead after loadDefer third-party JS; chunk long tasksPerformance panel long tasks, RUM traces

Budgets belong in CI, not in vibes. Wire Lighthouse CI into the pull request with hard gates — LCP budget 2.0s, initial JS under 170KB — and let the build fail. A performance budget enforced by memory and goodwill regresses within one sprint; one enforced by the pipeline regresses within one revert.

The dashboard that matters

Two data sources, two jobs. Lab data (Lighthouse, WebPageTest) is synthetic and reproducible — it diagnoses why, showing waterfalls and shift regions on a device profile you control. Field data (the Chrome UX Report feeding Search Console) is 28 days of real devices and real patience — it decides whether the problem exists. Lab tells you what to fix; field tells you if it mattered.

The operational habit is trend-watching, not one-off checks: track the p75 of each vital weekly, alert on regressions above a few percent, and annotate deploys so a spike gets a named cause within the hour.

The 75th-percentile rule. Core Web Vitals pass or fail at p75 of real users — the median user is not the exam. A site whose average is fast and whose tail is slow still fails, and the tail is precisely where the revenue leaks: mid-range Androids on hotel Wi-Fi are customers too.

The takeaway: stop filing Core Web Vitals under SEO. It is a conversion lever with a compliance story attached — fix the server, then the paint, then the stability, then the responsiveness, and measure the results in field data and revenue, not in a green badge on one fast laptop. The badge follows the revenue, not the other way around.
